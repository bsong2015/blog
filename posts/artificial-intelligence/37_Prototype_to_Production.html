摘要Abstract

核心目标：提供AI智能体运营生命周期的综合技术指南，重点关注部署、扩展和生产化

关键内容

🎯 核心主题

  • 如何通过强大的CI/CD流水线和可扩展基础设施建立必要的信任
  • 探索从原型到企业级解决方案的挑战
  • 特别关注Agent2Agent (A2A) 互操作性

👥 目标受众

  • AI/ML工程师
  • DevOps专业人员
  • 系统架构师

核心理念：Building an agent is easy. Trusting it is hard.（构建智能体很容易，信任它很难。）

介绍：从原型到生产Introduction: From Prototype to Production

挑战：你可以在几分钟甚至几秒钟内启动AI智能体原型，但将其转变为可靠的生产级系统？这才是真正工作的开始。

The "Last Mile" Production Gap

在"最后一英里"生产差距中，我们观察到：

80%的努力不是花在智能体的核心智能上，而是花在使其可靠和安全所需的基础设施、安全和验证上。

跳过这些步骤可能导致的问题

  • 客服智能体被欺骗免费赠送产品
  • 用户通过智能体访问机密内部数据库
  • 智能体产生大量消耗账单，但没有人知道原因
  • 关键智能体突然停止工作，团队束手无策

"最后一英里"生产差距The "Last Mile" Production Gap

智能体的独特挑战

❌ 传统ML模型

  • 遵循预定义路径
  • 静态执行流程
  • 可预测的行为

✅ AI智能体

  • 自主交互
  • 有状态
  • 动态执行路径

独特的运营头痛问题

🔧 动态工具编排

智能体的"轨迹"是动态组装的，需要强大的版本控制、访问控制和可观测性

📊 可扩展状态管理

智能体可以跨交互记忆，安全一致地管理会话和记忆是一个复杂的系统设计问题

⚡ 不可预测的成本和延迟

智能体可以采取许多不同的路径来找到答案，使其成本和响应时间难以预测和控制

解决方案：建立在三大关键支柱上：Automated Evaluation、Automated Deployment (CI/CD)、Comprehensive Observability

生产之旅The Journey to Production

核心原则：Evaluation-Gated Deployment（评估门控部署）- 没有智能体版本应该在没有通过证明其质量和安全的全面评估的情况下到达用户。

预生产阶段的三大支柱

📊 Evaluation

评估：

  • 严格的评估流程
  • 作为质量门
  • 评估行为质量，而不仅仅是功能正确性

🔄 CI/CD Pipeline

CI/CD流水线：

  • 自动化CI/CD流水线
  • 强制执行评估门
  • 分阶段测试，逐步建立信心

🛡️ Safe Rollout

安全部署：

  • 安全部署策略
  • 降低进入生产环境的最后一步的风险
  • Canary、Blue-Green、A/B测试、Feature Flags

评估作为质量门控Evaluation as a Quality Gate

为什么我们需要一个特殊的质量门？传统软件测试对于能够推理和适应的系统是不够的。

两种主要实现方式

📋 Manual "Pre-PR" Evaluation

手动"预PR"评估：

  • 通过团队流程强制执行质量门
  • AI工程师或提示工程师在提交PR之前运行评估套件
  • 性能报告链接在PR描述中
  • 评估结果成为人工审查的强制性工件

⚙️ Automated In-Pipeline Gate

自动化流水线门：

  • 评估套件直接集成到CI/CD流水线中
  • 失败的评估自动阻止部署
  • 提供刚性、程序化的质量标准执行
  • 如果关键指标低于预定义阈值，部署将被程序化阻止

关键点：无论采用哪种方法，原则都是一样的：没有质量检查，智能体不会进入生产环境。

自动化CI/CD流水线The Automated CI/CD Pipeline

定义：CI/CD（Continuous Integration/Continuous Deployment）流水线不仅仅是一个自动化脚本，它是一个结构化的流程，帮助团队中的不同人员协作管理复杂性并确保质量。

CI/CD流水线的设计

一个强大的流水线设计为漏斗，尽可能早且便宜地捕获错误，这通常被称为"左移"。

三个不同阶段：

  1. Phase 1: Pre-Merge Integration (CI) - 预合并集成
  2. Phase 2: Post-Merge Validation in Staging (CD) - 合并后验证
  3. Phase 3: Gated Deployment to Production - 门控部署到生产环境

关键基础设施：Infrastructure as Code (IaC) 和 Automated Testing Frameworks

CI/CD三阶段详解CI/CD Three-Stage Breakdown

🔍 Phase 1: Pre-Merge Integration (CI)

预合并集成：

  • 为打开PR的AI工程师或提示工程师提供快速反馈
  • 作为主分支的守门员
  • 运行快速检查：单元测试、代码linting、依赖扫描
  • 理想阶段：运行智能体质量评估套件
  • 防止污染主分支

🧪 Phase 2: Post-Merge Validation in Staging (CD)

合并后验证：

  • 将智能体打包并部署到staging环境
  • Staging是生产环境的高保真副本
  • 运行更全面、资源密集的测试
  • 负载测试和远程服务的集成测试
  • 内部用户测试（"dogfooding"）

🚀 Phase 3: Gated Deployment to Production

门控部署到生产环境：

  • 智能体在staging环境中经过全面验证
  • 几乎从不完全自动
  • 通常需要产品所有者给予最终批准
  • 确保人在循环中
  • 将在staging中测试和验证的确切部署工件提升到生产环境

关键基础设施：

  • Infrastructure as Code (IaC)：使用Terraform等工具以编程方式定义环境，确保它们相同、可重复和版本控制
  • Automated Testing Frameworks：使用Pytest等框架在每个阶段执行测试和评估
  • Secrets Management：使用Secret Manager等服务安全地管理敏感信息

安全部署策略Safe Rollout Strategies

核心理念：通过渐进式部署和仔细监控来最小化风险，而不是一次性切换100%的用户。

四种经过验证的模式

🐦 Canary

金丝雀部署：

  • 从1%的用户开始
  • 监控prompt注入和意外的工具使用
  • 逐步扩大或立即回滚

🔵 Blue-Green

蓝绿部署：

  • 运行两个相同的生产环境
  • 将流量路由到"blue"，同时部署到"green"
  • 然后瞬间切换
  • 如果出现问题，切换回来——零停机时间，瞬间恢复

🔬 A/B Testing

A/B测试：

  • 在真实的业务指标上比较智能体版本
  • 进行数据驱动的决策
  • 可以与内部或外部用户一起进行

🚩 Feature Flags

功能标志：部署代码但动态控制发布，首先与选定的用户测试新功能。

共同基础：严格的版本控制。每个组件——代码、提示、模型端点、工具schema、记忆结构，甚至评估数据集——都必须版本化。

从一开始构建安全Building Security from the Start

核心理念：智能体可以自主地推理和行动，需要一个从一开始就嵌入的综合治理策略，而不是事后添加。

智能体的独特风险

💉 Prompt Injection & Rogue Actions

Prompt注入和流氓行动：恶意用户可以欺骗智能体执行意外操作或绕过限制。

📤 Data Leakage

数据泄露：智能体可能通过其响应或工具使用无意中暴露敏感信息。

🧪 Memory Poisoning

记忆中毒：存储在智能体记忆中的虚假信息可能腐蚀所有未来的交互。

解决方案：Google's Secure AI Agents approach 和 Google Secure AI Framework (SAIF) 通过三层防御来应对这些挑战。

安全防御层Security Defense Layers

三层防御

📜 Policy Definition and System Instructions

策略定义和系统指令（智能体的宪法）：

  • 定义期望和不期望的智能体行为的策略
  • 这些被工程化为系统指令（SIs）
  • 作为智能体的核心宪法

🛡️ Guardrails, Safeguards, and Filtering

护栏、保障和过滤（执行层）：

  • Input Filtering：使用分类器和Perspective API分析提示并阻止恶意输入
  • Output Filtering：Vertex AI内置安全过滤器提供对有害内容的最终检查
  • HITL Escalation：对于高风险或模糊操作，系统必须暂停并升级到人工审查

🔄 Continuous Assurance and Testing

持续保证和测试：

  • Rigorous Evaluation：任何更改都必须触发全面重新运行评估流水线
  • Dedicated RAI Testing：通过创建专门的数据集或使用模拟智能体进行严格测试
  • Proactive Red Teaming：通过创造性的手动测试和AI驱动的基于角色的模拟主动尝试破坏安全系统

Observe-Act-Evolve循环

核心理念：有效的团队采用连续循环：实时观察系统行为，行动以维持性能和安全，基于生产学习演进智能体。

观察：智能体的感知系统Observe: Your Agent's Sensory System

定义：要信任和管理自主智能体，你必须首先理解其过程。可观测性提供了这种关键洞察。

三大支柱

📝 Logs

日志：

  • 精细的、事实的日记
  • 记录每个工具调用、错误和决策
  • 发生了什么的记录

🔗 Traces

追踪：

  • 连接单个日志的叙述
  • 揭示智能体采取特定行动的因果路径
  • 为什么智能体采取行动

📊 Metrics

指标：

  • 聚合的报告卡
  • 总结性能、成本和运营健康状况
  • 大规模显示系统运行情况

Google Cloud Operations Suite：Cloud Trace、Cloud Logging、Cloud Monitoring、Agent Development Kit (ADK)

行动：操作控制的杠杆Act: The Levers of Operational Control

定义："Act"阶段是关于实时干预——你根据观察到的内容拉动的杠杆，以管理智能体的性能、成本和安全。

操作杠杆的两大类别

💚 Managing System Health

管理系统健康：

  • Performance（性能）
  • Cost（成本）
  • Scale（规模）

🛡️ Managing Risk

管理风险：

  • Security Response Playbook（安全响应手册）
  • Contain（遏制）
  • Triage（分流）
  • Resolve（解决）

Act vs Evolve："Act"是系统的自动反射，旨在实时维持稳定性。"Evolve"是从行为中学习的战略过程，以创建根本更好的系统。

管理系统健康：性能、成本和规模Managing System Health: Performance, Cost, and Scale

挑战：与传统的微服务不同，智能体的工作负载是动态和有状态的。管理其健康需要处理这种不可预测性的策略。

Designing for Scale

🔧 Horizontal Scaling

水平扩展：

  • 将智能体设计为无状态、容器化服务
  • 任何实例都可以处理任何请求
  • Cloud Run或Vertex AI Agent Engine Runtime自动扩展

⏱️ Asynchronous Processing

异步处理：

  • 对于长时间运行的任务，使用事件驱动模式卸载工作
  • 保持智能体响应
  • 复杂任务在后台处理
  • Pub/Sub触发Cloud Run服务

Balancing Competing Goals

⚡ Speed (Latency)

速度（延迟）：

  • 并行设计
  • 积极缓存结果
  • 使用更小、高效的模型

✅ Reliability

可靠性（处理故障）：

  • 自动重试
  • 指数退避
  • 设计"安全重试"（幂等）工具

💰 Cost

成本：

  • 缩短提示
  • 使用更便宜的模型
  • 批量发送请求

进化：从生产中学习Evolve: Learning from Production

定义："Evolve"阶段是关于长期、战略改进。它从查看可观测性数据中收集的模式和趋势开始，并提出一个关键问题："我们如何解决根本原因，使这个问题不再发生？"

从反应到主动

❌ Reacting

反应：

  • 响应生产事件
  • 临时修复
  • 被动处理问题

主动改进：

  • 使智能体更智能、更高效、更安全
  • 改进智能体的架构、逻辑和行为

关键目标：从响应生产事件转向主动使你的智能体更智能、更高效、更安全。

Observe-Act-Evolve安全循环

Evolve的关键步骤：

  1. Update Evaluation Datasets：新的prompt注入攻击作为永久测试用例添加到评估套件中
  2. Refine Guardrails：提示工程师或AI工程师改进智能体的系统提示、输入过滤器或工具使用策略，以阻止新的攻击向量
  3. Automate and Deploy：工程师提交更改，触发完整的CI/CD流水线。更新的智能体针对新扩展的评估集进行严格验证，并部署到生产环境，关闭漏洞

超越单智能体操作Beyond Single-Agent Operations

挑战：当组织扩展到数十个专业智能体——每个都由不同团队使用不同框架构建时——出现了一个新挑战：这些智能体无法协作。

当前问题

  • 客服团队有他们的支持智能体
  • 分析团队构建了预测系统
  • 风险管理创建了欺诈检测
  • 但这些智能体无法相互对话——无论是由于它们是在不同的框架、项目甚至不同的云中创建的

解决方案：标准化协议可以将这些孤立的智能体转变为互操作的生态系统，通过智能体协作释放指数级价值。

A2A - 可重用性和标准化A2A - Reusability and Standardization

核心理念：你需要互操作性——任何智能体能够利用任何其他智能体的能力，无论谁构建它或使用什么框架。

两种互补协议

🔧 MCP (Model Context Protocol)

模型上下文协议：

  • 提供工具集成的通用标准
  • 适用于简单的、无状态函数
  • 例如：获取天气数据、查询数据库
  • MCP让你说："做这个具体的事情"

🤝 A2A (Agent2Agent)

智能体到智能体协议：

  • 设计用于智能体之间复杂、有状态的协作
  • 由Linux Foundation管理
  • 适用于委托复杂目标
  • A2A让你说："实现这个复杂的目标"

关键区别：MCP用于工具和资源——具有明确定义、结构化输入和输出的原语。A2A用于其他智能体——能够推理、计划、使用多个工具并维护状态以实现复杂目标的自主系统。

A2A协议：从概念到实现A2A Protocol: From Concept to Implementation

目标：A2A协议旨在打破组织孤岛，实现智能体之间的无缝协作。

应用场景

场景：欺诈检测智能体发现可疑活动。为了理解完整上下文，它需要来自单独的交易分析智能体的数据。

  • Without A2A：人工分析师必须手动弥合这一差距——这个过程可能需要数小时。
  • With A2A：智能体自动协作，在几分钟内解决问题。

Agent Cards

协作的第一步是发现正确的智能体来委托——这通过Agent Cards实现，Agent Cards是标准化的JSON规范，充当每个智能体的"名片"。

Agent Card描述：智能体可以做什么、其安全要求、其技能以及如何联系它（url），允许生态系统中的任何其他智能体动态发现其同行。

Agent Card示例Agent Card Example

示例：一个检查质数的智能体的Agent Card

{
  "name": "check_prime_agent",
  "version": "1.0.0",
  "description": "An agent specialized in checking whether numbers are prime",
  "capabilities": {},
  "securitySchemes": {
    "agent_oauth_2_0": {
      "type": "oauth2"
    }
  },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["application/json"],
  "skills": [
    {
      "id": "prime_checking",
      "name": "Prime Number Checking",
      "description": "Check if numbers are prime using efficient algorithms",
      "tags": ["mathematical", "computation", "prime"]
    }
  ],
  "url": "http://localhost:8001/a2a/check_prime_agent"
}

关键点：采用此协议不需要架构大修。ADK等框架大大简化了此过程。你可以通过单个函数调用使现有智能体与A2A兼容，该函数自动生成其AgentCard并使其在网络上可用。

A2A和MCP如何协同工作How A2A and MCP Work Together

核心理念：A2A和MCP不是竞争标准；它们是设计在不同抽象层次上运行的互补协议。

汽车维修店类比

  1. User-to-Agent (A2A)：客户使用A2A与"Shop Manager"智能体通信，描述高级问题："我的车发出嘎吱声。"
  2. Agent-to-Agent (A2A)：Shop Manager进行多轮诊断对话，然后将任务委托给专门的"Mechanic"智能体，再次使用A2A。
  3. Agent-to-Tool (MCP)：Mechanic智能体现在需要执行特定操作。它使用MCP调用其专用工具：在诊断扫描仪上运行scan_vehicle_for_error_codes()，使用get_repair_procedure()查询维修手册数据库，并使用raise_platform()操作平台升降机。
  4. Agent-to-Agent (A2A)：诊断问题后，Mechanic智能体确定需要零件。它使用A2A与外部"Parts Supplier"智能体通信，询问可用性并下订单。

关键点：A2A促进客户、商店智能体和外部供应商之间的高级、对话式和面向任务的交互。同时，MCP提供标准化管道，使mechanic智能体能够可靠地使用其特定、结构化工具来完成工作。

注册中心架构：何时以及如何构建Registry Architectures: When and How to Build Them

核心问题：为什么有些组织构建注册中心而其他组织不需要？答案在于规模和复杂性。

两种注册中心

🔧 Tool Registry

工具注册中心：

  • 使用MCP等协议编目所有资产
  • 从函数到API
  • 创建策划列表，而不是给智能体访问数千个工具
  • 三种常见模式：Generalist agents、Specialist agents、Dynamic agents

🤝 Agent Registry

智能体注册中心：

  • 使用A2A的AgentCards等格式
  • 帮助团队发现和重用现有智能体
  • 减少冗余工作
  • 为自动化智能体到智能体委托奠定基础

何时构建：

  • Tool Registry：当工具发现成为瓶颈或安全需要集中审计时构建
  • Agent Registry：当多个团队需要发现和重用专业智能体而无需紧密耦合时构建

权衡：注册中心提供发现和治理，但需要维护。你可以考虑开始时不使用注册中心，只有当你的生态系统规模需要集中管理时才构建它！
